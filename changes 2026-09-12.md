The following changes need to be made:

1. The main change is the addition of new `/v2` endpoints. This is the new minimalist API that we settled on after prototyping. The structure of their requests and responses is described in the Markdown file @payload-v2-am-aa.md. In these versions,
   there is no concept of components; for all operations, we treat the entire field as a whole and perform
   optimization across all cells without any partitioning (tests showed that this approach allows the algorithm to reach a better solution, while the performance gain is not comparable to the implementation complexity). Redundant fields have also been removed from requests and responses; everything
   should become concise.
2. Bar layout (`bar_layout`) should additionally have a separate `/v2/bars` endpoint that receives zones in the format described in @payload-v2-am-aa.md. The endpoint should return bars.

3. Bar validation must no longer run after any PUT request; it should only be performed through a separate endpoint. The validation
   mechanism has also changed. First, bar layout must be performed for these zones, as before, and then
   reinforcement must be calculated for each component. In the scene, it is initially specified in cm²/m. In the output, the actual reinforcement
   and the requirement must be calculated in two units, including kg/m³. To obtain the actual reinforcement in cm²/m, calculate
   the volume of bars that falls within the polygon (intersect the bar axes with the polygon and represent each bar as
   a cylinder with its own radius, then sum them) and divide it by the polygon area. For the kg/m³ calculation, use the specified
   steel density and concrete thickness `t`.

4. Keep in mind that all zone and bar geometry must now be stored and transferred without anchorage!! Anchorage
   is used only in the solver, in mass calculations, and when coloring the final bars. If an original
   bar extends beyond the boundaries, it must be clipped, but starting from that clipped edge the anchorage must still
   exist invisibly and its mass must still be included.

5. Currently, all operations are executed by a single worker type. We now have two new task types (`/v2/bars`, `/v2/verifications`). Separate entrypoints and ScaledJobs must be created for them so that they run as two independent, isolated processes.

The main task gets more detailed state reporting (new statuses in addition to the basic `pending`/`success`/`error`/`cancelled`):

- `preparing` — must calculate `max_useful_n` for the entire scene and then run `prepare_problem` for the solver,
  passing the resulting value to it. All operations must happen entirely within this stage; it must not call the old worker or
  any other worker types. Almost like `prepare_whole`.
- `solving` — a separate stage specifically for the solver. Analogous to `solve_whole`.
- `fitting` — also moved into a separate stage. Like `fit_whole`.
- `bars` — analogous to `layout_solution`; performs the complete bar layout.


6. Implement and verify that all deployment-control parameters that are nevertheless controlled through the API (for example, the number of workers per task, the number of HiGHS threads, the number-of-zones values for `prepare_problem`, etc.) are either completely removed from the process or taken ONLY from environment variables defined in the ConfigMap,
that is, the ConfigMap must be the sole source of these parameters. Currently they can be set in all sorts of places. Also remove all checks and validation related to setting these parameters that could prevent arbitrary values from being supplied through the ConfigMap (for example, the number of workers per task).


7. In every worker that executes a reinforcement-selection task, mount a shared CSI-S3 directory, for example at `./logs`, and direct HiGHS logs to `{task_id}/{n}/{worker-id}.log` for additional debugging and monitoring. Create a separate CSI-S3 PVC for this directory and a shared `rebar-optimizer/logs` directory, mounted via `subPath` into each worker.
Before initializing the solver in the worker, set `h.setOptionValue("log_file", "<app-directory>/logs/{task_id}/{n}/{worker-id}.log")`, where `<app-directory>` is a placeholder.
